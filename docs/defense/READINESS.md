# Readiness and later professor mode

## Preparation status

The study materials and code map are prepared. Your understanding and demonstration ability have not yet been evaluated. No personal readiness score or university grade is assigned from source inspection alone.

Work through the tutor stages in order. For each stage, open the code, explain one real path in your own words, perform the demonstration and predict an invalid request before trying it. The readiness assessment comes after this preparation, not merely after downloading the documents.

## High risk

- Confusing package/folder names with architecture: shared Flutter implementation, service locator/direct HTTP exceptions, controller-direct EF paths.
- Claiming complete role/ownership security: show actual policies and acknowledge inherited reservation read gap, stale JWT claims and exact role names.
- Product State pattern: exact states/operations, deactivated update only changes state, generic delete outside pattern, independent IsActive and weak catalogue/checkout guards.
- Transactions/concurrency: booking creation versus update, order/return update locks, SQL versus external provider effects, bracket/result multi-save limits.
- RabbitMQ: producer/outbox/publisher/consumer/inbox, duplicate delivery window and current log-only side effect; no exactly-once or real-time UI claim.
- Payment/notification provider claims: order is not payment; readiness is not provider success; provider success is not user receipt; local Mailpit is not external delivery.
- Recommendation evidence: demo signals versus eligible operational evaluation, temporal leakage/returns/maturity, external dataset versus club performance, descriptive attribution versus causal lift.

## Medium risk

- Explaining UI versus backend versus SQL validation and the actual 400/409/404/204 behavior of a chosen endpoint.
- Pagination and capped local filters, the shop TotalCount omission, IQueryable versus List operations.
- FK/nullability/delete rules; the distinction between an Id scalar, navigation and real constraint.
- Refresh storage/rotation/reuse, email verification and recovery expiry, fixed client refresh timer.
- Membership lifecycle, return quantities/refund allocation, tournament partner response/byes and match confirmation requirements.
- Docker port/DNS/volume behavior and bootstrap readiness; API startup alone does not prove a usable database.
- Async dependencies, DbContext lifetime and the reason hosted workers create scopes.

## Low risk after basic rehearsal

- Reaching the five mobile destinations and desktop management pages.
- Ordinary UI form entry, basic add/edit/read, showing a successful refreshed result.
- Naming core entities and locating controller/service/request files.
- Describing visible read-only account/payment/audit screens accurately.

Low risk does not mean demonstrated proficiency; it means simpler material to master.

## The gate before examination

After the guided preparation, summarize what you can explain/show and what remains uncertain. Only then the tutor can say:

**“You are now ready to begin the mock defense.”**

Do not begin the examination in that same message. Wait for your explicit **“Start the defense.”** instruction. The quoted statement here describes the later gate; it is not a current assessment that you are ready.

## Professor mode protocol

When explicitly started, the first task is:

“Start the entire system and briefly explain its architecture. Tell me what the desktop application is responsible for, what the mobile application is responsible for, and what role the backend and database have.”

Then ask one main question/task at a time and wait for your answer. Evaluate first, then continue. No answer/hint is supplied before your attempt unless you explicitly request a hint. Increase difficulty from what → how → why → what if as performance allows.

Regularly require showing the live screen, record, API endpoint, ownership guard, state method, SQL FK, outbox row or subscriber log. Select tasks from the actual map. Include at least one desktop/mobile shared-record workflow, an invalid API request, role restriction, state transition/rejection, database trace and messaging explanation. Adapt order naturally and occasionally change the requested view to prevent memorized navigation.

For each answer, internally record accuracy, completeness, independence and demonstration evidence across: desktop, mobile, backend, database, architecture, business logic, authentication, authorization, validation, APIs, State pattern, RabbitMQ, Docker, code understanding, demonstration ability and unexpected follow-ups. A failed runtime demonstration and a correct source explanation are different evidence; record both honestly. Do not count a requested hint as an independent correct answer.

At the end provide strengths, weaknesses, incorrect answers with corrections, dangerous gaps, practice-again questions, exact code to review, readiness score 1–10 and a realistic mock grade. If the institution's grade scale has not been supplied, explicitly state the scale used rather than assuming it from location.
